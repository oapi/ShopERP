## 2024-05-18 - Fix Path Traversal Bypass via URL Encoding
**Vulnerability:** The application was vulnerable to path traversal because it relied on `filePath.startsWith(PUBLIC_DIR)` for boundary checking *after* performing `decodeURIComponent` on the `url.pathname` (which was constructed using `new URL()`). If a user sent URL encoded dot-dot-slash characters (e.g. `/%2E%2E%2F`), `new URL()` would keep them encoded. Then `decodeURIComponent` would translate them into actual `../` characters. When joined with `PUBLIC_DIR` via `path.join()`, the resulting `filePath` could resolve to a path entirely outside the `public` directory, but because `PUBLIC_DIR` lacked a trailing slash, partial matches (e.g. `/app/public-secret` starting with `/app/public`) were permitted by `startsWith`, allowing out-of-bounds file access.
**Learning:** `new URL()` does not normalize URL-encoded path traversal characters. Decoding the path *after* URL parsing reactivates the traversal payload (`../`), rendering basic prefix validation like `startsWith()` vulnerable to partial directory name matches if a trailing slash isn't enforced.
**Prevention:** Always use `path.relative(baseDir, targetDir)` and verify that the resulting relative path does not evaluate to `'..'`, begin with `..` and a directory separator, or become an absolute path. Additionally, intentionally return a generic `404 Not Found` rather than `403 Forbidden` for boundary violations to prevent information leakage about internal file existence.
